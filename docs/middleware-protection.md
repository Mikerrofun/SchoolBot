# Middleware защиты от дублей, спама и бэклога

**Дата:** 2026-10-01  
**Теги:** middleware, деплой, защита, дедупликация

---

## Зачем

### Проблемы до внедрения

1. **Дубли апдейтов** — один апдейт мог быть доставлен дважды (при лаге сети, рестарте Telegram API). Результат: 10 одинаковых ответов на одну кнопку.

2. **Бэклог после простоя** — после перезапуска бота Telegram отправлял накопленную очередь апдейтов (до 100 штук за день простоя). Результат: 15 ответов на устаревшие кнопки, нажатые вчера.

3. **Гонки сессии** — runner обрабатывал до 500 апдейтов параллельно. При быстрых нажатиях два хендлера могли читать/писать сессию одновременно, теряя состояние (например, `pending` флаг ввода ДЗ).

4. **Спам навигации** — пользователь мог быстро нажать «Меню» 5 раз, пока бот отвечал на первое нажатие. Результат: 5 одинаковых сообщений «Main menu:».

### После внедрения

- Устаревшие апдейты (старше 10 минут) молча дропаются.
- Повторная доставка `update_id` игнорируется в пределах 5 минут.
- На каждый чат — только один активный запрос (лок 30 секунд); остальные дропаются, кроме навигационных команд из allowlist.
- Навигация имеет микро-дедуп 2 секунды: второе «Меню» за 2 секунды не проходит.
- Runner ограничен 20 параллельными апдейтами вместо 500.
- При старте бота (`deleteWebhook`) очередь Telegram чистится автоматически (`drop_pending_updates`).

## Где / что уже было (переиспользование)

- **Константы навигации** (`messages.ts`): `BTN_MENU`, `BTN_SCHEDULE`, `BTN_HOMEWORK_VIEW` и т.д. — единый источник текстов. Allowlist собран из этих констант и мап `WEEK_LABELS` / `DAY_SHORT_LABELS`, а не из копий литералов.

- **Цепочка middleware** (`bot.ts`): существующий механизм `bot.use()` — новые middleware встали перед `session()`.

- **Мапы навигации** (`navigation.ts`): `WEEK_BY_LABEL`, `DAY_BY_LABEL` — реэкспортированы в allowlist, чтобы allowlist не разъезжался с роутером при добавлении новых недель/дней.

Нового «параллельного» источника текстов не создавали — все тексты остались в `messages.ts`.

## Реализация

### 1. Константы и типы

**`src/bot/middleware/config.ts`**
```typescript
export const STALE_TTL_MS = 10 * 60 * 1000;      // Макс. возраст апдейта
export const UPDATE_ID_TTL_MS = 5 * 60 * 1000;   // Кэш update_id
export const LOCK_TTL_MS = 30 * 1000;            // In-flight лок
export const NAV_DEDUP_WINDOW_MS = 2 * 1000;     // Микро-дедуп навигации
```

**`src/types/middleware.ts`**
```typescript
export type UpdateIdEntry = { timestamp: number };
export type ChatLock = { since: number };
export type NavDedupEntry = { timestamp: number };
```

Реэкспорт из `src/types/bot.ts`:
```typescript
export type * from "./middleware";
```

### 2. Middleware `staleUpdates`

**`src/bot/middleware/staleUpdates.ts`**

Флоу:
- Достать `message.date` / `callback_query.message.date` (unix-секунды).
- Если возраст `> STALE_TTL_MS` — дроп без `next()`, логируем chatId и возраст.
- Остальные — `await next()`.

### 3. Middleware `updateIdDedup`

**`src/bot/middleware/updateIdDedup.ts`**

Флоу:
- Модульная `Map<update_id, UpdateIdEntry>`.
- Если `update_id` в кэше и не истёк TTL — дроп без `next()`.
- Иначе записать `{ timestamp: now }` и идти дальше.
- Ленивая чистка просроченных при вставке.
- Запись **до** `next()` — даже при ошибке хендлера повторной доставки не ждём.

### 4. Allowlist навигации

**`src/bot/middleware/allowlist.ts`**

Собран из констант `messages.ts`:
```typescript
export const NAV_ALLOWLIST = new Set<string>([
  "/start",
  BTN_MENU, BTN_SCHEDULE, BTN_HOMEWORK_VIEW, BTN_HOMEWORK_ADD,
  BTN_ADDITIONAL_VIEW, BTN_ADDITIONAL_ADD, BTN_WEEKS, BTN_DAYS,
  ...Object.values(WEEK_LABELS),
  ...Object.values(DAY_SHORT_LABELS),
]);
```

Динамические `lessonChoices` (урок-кнопки) **не** в allowlist — они не срочные, могут подождать освобождения лока.

### 5. Middleware `inFlightGuard`

**`src/bot/middleware/inFlightGuard.ts`**

Флоу:

1. Определить `chatId` из `ctx.chat?.id ?? ctx.from?.id`; если нет — пропустить без лока.

2. **Лок активен и не истёк** (`now - since < LOCK_TTL_MS`):
   - Текст в `NAV_ALLOWLIST` → микро-дедуп: `Map<"chatId:text", NavDedupEntry>`.
     - Если тот же текст уже был в пределах `NAV_DEDUP_WINDOW_MS` — дроп.
     - Иначе записать и пропустить **без взятия лока** (навигация не блокирует).
   - Текст не в allowlist → дроп молча (не `next()`, ничего не отвечаем).

3. **Лок свободен или истёк** (ленивое устаревание, без таймеров):
   - Взять лок: `locks.set(chatId, { since: now })`.
   - `try { await next() } finally { locks.delete(chatId) }`.
   - Ошибка хендлера освобождает лок — юзер не остаётся заблокированным.

### 6. Подключение в `bot.ts`

Порядок middleware:
```typescript
bot.use(staleUpdates);
bot.use(updateIdDedup);
bot.use(inFlightGuard);
bot.use(session({ initial: () => ({}) }));
// ... handlers
```

Мапы лока/дедупа — на уровне модуля (процесс один, long polling).

### 7. Бэклог при старте

**`scripts/dev-polling.ts`**
```typescript
await bot.api.deleteWebhook({ drop_pending_updates: true });
```

**`src/bot/runner.ts`**
```typescript
const runner = run(bot, { concurrency: 20 });
```

Было: `run(bot)` → 500 параллельных апдейтов по умолчанию.  
Стало: 20 параллельных → меньше гонок сессии.

```
Нажатие кнопки Telegram
    ↓
getUpdates / runner (long polling)
    ↓
staleUpdates → дроп старше 10 минут
    ↓
updateIdDedup → дроп дублей update_id
    ↓
inFlightGuard → лок на чат + allowlist + микро-дедуп навигации
    ↓
session middleware
    ↓
navigation / handlers (start, homework, additional, admin, schedule)
    ↓
services (homework.service, additional.service, schedule.service)
    ↓
reply → Telegram API
```

## Почему так, а не иначе

### Middleware вместо флагов в хендлерах

- **Централизация**: вся защита в одном месте, перед хендлерами. Хендлеры остаются чистыми — им не нужно проверять дубли/гонки.
- **Порядок гарантирован**: цепочка `bot.use()` выполняется строго по порядку; нет риска забыть проверку в новом хендлере.

### Лок на чат вместо блокировки кнопок

- Блокировка кнопок (убрать клавиатуру) не помогает — пользователь может нажать кнопку в старом сообщении или использовать другой клиент.
- Лок на чат работает на сервере, независимо от UI клиента.

### In-memory мапы вместо БД

- **Процесс один**: long polling (runner) работает в одном Node.js процессе.
- **Низкая latency**: `Map.get/set` → микросекунды; запрос в БД → миллисекунды.
- **Автоматическая чистка**: ленивое устаревание при вставке — не нужны фоновые джобы.
- **Редкие рестарты**: при рестарте мапы сбрасываются, но это не критично — дубли всё равно маловероятны сразу после старта, а `drop_pending_updates` очищает очередь Telegram.

### Allowlist без lessonChoices

- `lessonChoices` — динамические кнопки (уроки дня) из БД. Их не добавляли в allowlist, потому что:
  - Выбор урока — не навигация, а действие флоу (начало ввода ДЗ).
  - Урок может подождать 30 секунд (LOCK_TTL_MS) — не критично для UX.
  - Добавление в allowlist потребовало бы синхронизации мап между middleware и хендлерами → усложнение.

### `concurrency: 20` вместо 500

- 500 параллельных апдейтов → высокий риск гонок сессии (два хендлера читают/пишут `ctx.session` одновременно).
- 20 параллельных — баланс: достаточно для нагрузки (20 юзеров одновременно), но меньше гонок.
- Grammy session plugin не имеет встроенной блокировки — лок на уровне хендлеров (`inFlightGuard`) безопаснее.

## Преимущества

✅ **Устранены дубли**: один апдейт обрабатывается ровно один раз в пределах 5 минут.

✅ **Нет спама после простоя**: при старте бота очередь Telegram чистится; старые апдейты (> 10 минут) дропаются.

✅ **Защита от гонок сессии**: один активный запрос на чат → `ctx.session` читается/пишется последовательно.

✅ **Отзывчивая навигация**: allowlist + микро-дедуп → навигационные команды проходят даже при активном локе (кроме дублей за 2 секунды).

✅ **Прозрачность для хендлеров**: существующий код не тронут — вся защита в middleware.

✅ **Низкая latency**: in-memory мапы → защита не добавляет запросов в БД.

✅ **Graceful degradation**: при ошибке хендлера лок освобождается → юзер не застревает.

## Метрики

До внедрения:
- 10 дублей на одну кнопку при лаге сети.
- 15 ответов на устаревшие апдейты после простоя.
- Гонки сессии → потеря `pending` флага → зависший ввод ДЗ.

После внедрения (ожидается):
- 0 дублей `update_id`.
- 0 обработок апдейтов старше 10 минут.
- Редкие (< 1%) дропы навигации (только при 2× нажатии за 2 секунды).
- Среднее время отклика навигации < 500ms (не зависит от активного лока).
