## 1. О проекте

  

**SchoolBot** — Telegram-бот школьного класса на **Next.js (App Router) +

grammY + Prisma + PostgreSQL**. Бот живёт внутри Next.js-приложения как

serverless-обработчик вебхука `POST /api/telegram/webhook`.

  

Возможности:

  

- 📅 **Расписание** — расписание текущей недели одним сообщением (день — уроки, без ДЗ).

- 📝 **Домашнее задание** — просмотр по дням (прошлая / текущая / следующая неделя).

- ✏️ **Добавить ДЗ** — выбор недели → дня → урока → ввод текста.

- 📌 **Дополнительно** — шестой «виртуальный» раздел, запись по дням недели.

- 🤖 **AI-проверка** — цензура текста перед сохранением и сравнение нового ДЗ

с существующим (OpenRouter, модель `google/gemini-3.6-flash`).

- ✅ **Модерация** — спорные ДЗ уходят админам на подтверждение кнопками.

`lib/errors.ts`, даты/недели — только через `lib/weeks.ts`. Хендлеры не

хардкодят строки и не считают даты сами.

## 4. Поток данных: от Telegram до ответа

  

```

Telegram → POST /api/telegram/webhook?secret=…

→ проверка секрета (401 + JSON при ошибке)

→ initBot() → grammY обрабатывает апдейт

→ хендлеры (navigation → flow-хендлеры → admin)

→ services → Prisma → PostgreSQL

→ ctx.reply(...) → Telegram API

→ всегда 200 {"ok":true} (чтобы Telegram не ретраил)

```

  

Вебхук (`src/app/api/telegram/webhook/route.ts`) — единственная точка входа.

Он никогда не «падает»: любая ошибка сериализуется в структурированный JSON

из реестра ошибок:

  

```ts

// Ответ при неверном секрете (HTTP 401):

{ "ok": false, "error": { "code": "UNAUTHORIZED", "message": "Неавторизованный запрос." } }

// Ответ при ошибке обработки (HTTP 200 — Telegram не должен ретраить):

{ "ok": false, "error": { "code": "UNKNOWN", "message": "Произошла ошибка, попробуйте позже." } }

```

  

Порядок регистрации хендлеров в `bot.ts` важен — роутер навигации стоит

**первым** среди текстовых обработчиков, поэтому нажатие любой кнопки

отменяет ожидающийся свободный ввод до того, как его увидят флоу-хендлеры:

  

```ts

registerStartHandler(bot); // /start, /menu

registerNavigationHandlers(bot); // reply-кнопки: меню, недели, дни, уроки

registerScheduleHandlers(bot); // /расписание

registerHomeworkHandlers(bot); // свободный текст ДЗ (pending)

registerAdditionalHandlers(bot); // свободный текст «Дополнительно» (pending)

registerAdminHandlers(bot); // inline approve/reject

```

## 5. Модель навигации: reply-клавиатуры + сессия

  

### 5.1. Два типа клавиатур

  

- **Reply-клавиатуры** (`Keyboard`, под полем ввода) — вся навигация: меню,

недели, дни, уроки. Приходят как обычные текстовые сообщения.

- **Inline-клавиатуры** (в сообщении) — только там, где нужен контекст

сообщения: подтверждение/отклонение ДЗ админом (`hw:approve:{id}` /

`hw:reject:{id}`).

  

Почему так: reply-кнопки всегда видны пользователю (не нужно листать чат до

старого сообщения), а состояние кнопок можно перерисовывать на каждом шаге.

  

### 5.2. Состояние в сессии

  

```ts

// src/types/bot.ts

export type SessionData = {

pending?: PendingInput; // что пользователь сейчас вводит текстом

flow?: Flow; // "hwv" | "hwa" | "adv" | "ada"

weekOffset?: WeekOffset; // -1 | 0 | 1 — выбранная неделя

lessonChoices?: LessonChoice[] // уроки, показанные reply-кнопками

};

```

  

`lessonChoices` — мост между reply-кнопками уроков и их id в БД: reply-кнопка

несёт только текст («1. Физра»), поэтому при показе списка роутер запоминает

соответствие «текст → урок»:

  

```ts

// navigation.ts, шаг выбора дня во флоу "hwa"

const choices: LessonChoice[] = lessons.map((lesson) => ({

lessonId: lesson.id,

label: `${lesson.lessonNumber}. ${shortSubject(lesson.subject)}`,

subject: lesson.subject,

dateKey: dateKeyOf(date),

}));

ctx.session.lessonChoices = choices;

await ctx.reply(`${dayTitle(date)}\n\n${PICK_LESSON_TEXT}`, {

reply_markup: lessonsReplyKeyboard(choices),

});

```

  

### 5.3. Роутер кнопок

  

Роутер (`handlers/navigation.ts`) матчит текст сообщения **с теми же

константами**, из которых строятся клавиатуры, — рассинхрон невозможен:

  

```ts

if (text === BTN_MENU) return showMainMenu(ctx);

if (text === BTN_SCHEDULE) return showSchedule(ctx);

if (text === BTN_HOMEWORK_VIEW) return startFlow(ctx, "hwv");

// …

if (text === BTN_WEEKS) return handleWeeksButton(ctx); // « Недели

if (text === BTN_DAYS) return handleDaysButton(ctx); // « Дни

  

const weekOffset = WEEK_BY_LABEL.get(text); // «Прошлая неделя» и т.д.

const day = DAY_BY_LABEL.get(text); // «Пн»…«Пт»

const choice = ctx.session.lessonChoices?.find((c) => c.label === text);

```

  

Кнопки возврата работают из любого места флоу: «« Недели» открывает пикер

недель **текущего** флоу, «« Дни» — пикер дней текущей недели. Если состояние

сессии потеряно (перезапуск serverless-инстанса), пользователь мягко

возвращается в главное меню вместо ошибки.

  

**Инвариант:** каждая перерисовка клавиатуры синхронизирует сессию с тем, что

видит пользователь. Например, после сохранения ДЗ бот отвечает текстом и

снова показывает клавиатуру дней, а `lessonChoices` очищается.

## 6. Пользовательские сценарии (флоу)

  

### 6.1. Расписание — без пикеров

  

Шаблон расписания одинаков каждую неделю (см. `schedule-template.ts`), поэтому

выбор недели/дня убран: кнопка «📅 Расписание» сразу отправляет одно сообщение

с текущей неделей и возвращает клавиатуру меню:

  

```

📅 Расписание

  

Понедельник (21.09)

1. Алгебра

2. Физра

…

  

Вторник (22.09)

…

```

  

```ts

export async function showSchedule(ctx: MyContext): Promise<void> {

// сброс состояния — флоу одношаговый

const days = await getWeekLessons(getWeekWindow(0)); // Пн–Пт текущей недели

await ctx.reply(scheduleWeekMessage(days), { reply_markup: mainMenuReplyKeyboard() });

}

```

  

### 6.2. Просмотр ДЗ (`hwv`)

  

`Меню → «📝 Домашнее задание» → неделя → день`. Один день — одно сообщение:

все уроки с текстом ДЗ (пустые — «—») и строка «📌 Дополнительно». Админ

дополнительно видит `⏳ на подтверждении:` с pending-текстом.

  

### 6.3. Добавление ДЗ (`hwa`)

  

`Меню → «✏️ Добавить ДЗ» → неделя → день → урок (reply-кнопки) → текст`.

После выбора урока `pending = { type: "lesson", … }`, и следующее свободное

сообщение пользователя трактуется как текст ДЗ. Повторное нажатие кнопки

урока переключает урок; нажатие дня/недели/меню отменяет ввод.

  

### 6.4. «Дополнительно» (`adv` — просмотр, `ada` — запись)

  

Просмотр показывает всю неделю сразу (`Пн: текст`, пустое — «—»). Запись:

`неделя → день → текст`, сохранение upsert'ом по дате. В пикере дней флоу

`hwa` есть кнопка «✏️ Дополнительно» — короткий переход в `ada` с той же

неделей.

## 7. AI-проверка ДЗ: как фича встроена в процессы

  

AI — **опциональный** слой: без `OPENROUTER_API_KEY` или при недоступности

OpenRouter бот продолжает работать. Оба вызова идут через один helper

`callOpenRouterJson` (15-секундный таймаут, `temperature: 0`,

`response_format: json_object`, zod-схема) и возвращают `null` = «вердикт

неизвестен». Каждый вызывающий обязан обработать `null` явно.

  

### 7.1. Цензура — ДО сохранения

  

`checkTextOnTopic(text)` решает, похож ли текст на запись по делу (ДЗ,

напоминание, примечание к уроку). Мусор (спам, реклама, мат, бессмыслица)

отклоняется. Проверка стоит **первым шагом** в обоих вводах — отклонённый

текст не создаёт и не меняет ничего:

  

```ts

// homework.ts — ввод текста ДЗ

const verdict = await checkTextOnTopic(ctx.message.text);

if (verdict === false) {

await ctx.reply(ERROR_REGISTRY.CONTENT_REJECTED, {

reply_markup: daysReplyKeyboard("hwa"),

});

return; // ничего не сохранено

}

const result = await saveHomework({ lessonId: pending.lessonId, … });

```

  

Политика при `null` (AI недоступен): **текст сохраняется** — для ДЗ дальше

сработает сравнение/модерация, для «Дополнительно» запись просто сохранится.

Ложные блокировки хуже пропущенного спама в школьном классе.

  

### 7.2. Сравнение — при перезаписи ДЗ

  

`compareHomework(existing, incoming)` в��зывается из `saveHomework`

**только когда ДЗ для урока уже существует**. Вердикт определяет судьбу записи:

  

| Вердикт AI | Действие | Что видит ученик |

|---|---|---|

| `same=true, betterText` | заменить `text` улучшенной формулировкой, `APPROVED` | «✅ ДЗ обновлено (AI улучшил формулировку)» |

| `same=true`, без betterText | оставить как есть | «ℹ️ Такое ДЗ уже записано» |

| `same=false` (другое задание) | новое → `pendingText`, статус `PENDING`; старое `text` остаётся видимым | «⏳ отправлено админу на подтверждение» |

| `null` (AI недоступен) | то же, что `same=false`, но админам уходит пометка «AI down» | «⚠️ AI-проверка временно недоступна…» |

  

```ts

// homework.service.ts — ядро логики

const comparison = await compareHomework(existing.text, trimmed);

  

if (comparison?.same) {

if (comparison.betterText && comparison.betterText !== existing.text) {

// замена улучшенной формулировкой, сразу APPROVED

}

return { action: "kept", … }; // то же задание — ничего не меняем

}

  

// другое задание ИЛИ AI недоступен → ручная модерация

const updated = await prisma.homework.update({

where: { lessonId },

data: { pendingText: trimmed, pendingCreatedBy: createdBy, status: "PENDING" },

});

```

  

Дизайн-решение: **одобренный текст никогда не перезаписывается молча**.

Всё, что AI не смог уверенно признать «тем же заданием», попадает в

`pendingText` и ждёт человека. Повторная отправка, пока запись в `PENDING`,

просто перезаписывает `pendingText` (последняя версия выигрывает).

  

### 7.3. Полная последовательность добавления ДЗ

  

```

Ученик: текст ДЗ

→ checkTextOnTopic (цензура; false → отказ, стоп)

→ saveHomework

→ ДЗ ещё нет? → создать, APPROVED, «✅ ДЗ записано»

→ compareHomework

→ same+better → обновить text

→ same → оставить

→ false/null → pendingText + PENDING

→ уведомление всем админам (кнопки ✅/❌)

→ автору: «⏳ отправлено на подтверждение»

```

## 8. Модерация админом

  

`notifyAdminsNewHomework` рассылает всем админам (`ADMIN_IDS` из env) сообщение

вида «причина → автор → предмет/день → Прошлое ДЗ / Новое ДЗ» с inline-кнопками:

  

- **✅ Подтвердить** — `approveHomework`: `pendingText` становится `text`,

автором записи становится отправитель pending-версии; автору летит

«✅ Твоё ДЗ подтверждено».

- **❌ Отклонить** — `rejectHomework`: `pendingText` очищается, старый `text`

остаётся; автору летит «❌ Твоё ДЗ отклонено админом».

  

Проверка прав — серверная (`isAdmin(ctx.from?.id)`), а не только скрытие

кнопок: не-админ, дёрнувший callback, получает alert «Подтвердить может

только админ». После решения сообщение помечается

«✅ Подтверждено админом» / «❌ Отклонено админом» (editMessageText).

## 9. Реестр ошибок

  

Все ошибки — с стабильными кодами и одним текстом на код

(`src/lib/errors.ts`). Хендлеры бросают `BotError` или читают

`ERROR_REGISTRY` для пользовательских отказов; вебхук сериализует ошибки в

JSON, `bot.catch` отвечает пользователю текстом из реестра:

  

```ts

export const ERROR_REGISTRY: Record<ErrorCode, string> = {

UNKNOWN: "Произошла ошибка, попробуйте позже.",

BOT_NOT_CONFIGURED: "Бот не настроен: отсутствует токен.",

UNAUTHORIZED: "Неавторизованный запрос.",

AI_UNAVAILABLE: "AI-проверка временно недоступна, попробуйте позже.",

CONTENT_REJECTED: "❌ Текст не похож на запись по делу…",

};

```

## 10. Пользователи

  

Модель `User` (telegramId уникален, username/имя/фамилия) заполняется

**только на `/start`** (upsert — повторный `/start` обновляет профиль).

Используется для человекочитаемого автора в админ-уведомлении:

`👤 Автор: Иван @ivanov (id: 123)`; если записи нет — просто id.

## 11. Схема БД (Prisma)

  

- **Lesson** — урок конкретной даты (`date + lessonNumber` уникальны),

`day`, `subject`. Создаётся лениво из `SCHEDULE_TEMPLATE` при первом

обращении к неделе (идемпотентно). Урок с «УПК» в среду автоматически

получает постоянное ДЗ-шутку.

- **Homework** — 1:1 к уроку: одобренный `text`, `pendingText` +

`pendingCreatedBy` (версия на модерации), `status: APPROVED | PENDING`,

`createdBy` (telegram id).

- **AdditionalHomework** — «Дополнительно», одна запись на дату, без модерации.

- **User** — профиль участника класса (см. §10).

## 13. Ключевые архитектурные решения (сводка)

  

1. **Reply-клавиатуры вместо inline для навигации** — кнопки всегда под

рукой, состояние перерисовывается на каждом шаге; inline остались только

у модерации, где нужна привязка к конкретному сообщению/записи.

2. **Роутер по константам** — клавиатуры и роутер используют одни и те же

константы из `messages.ts`, поэтому кнопка не может «потеряться».

3. **Сессия как единственное состояние флоу** — `flow/weekOffset/pending/

lessonChoices`; любое нажатие навигации отменяет pending-ввод.

4. **Расписание без пикеров** — шаблон одинаков каждую неделю, поэтому кнопка

отдаёт неделю одним сообщением (меньше шагов и сообщений).

5. **AI опционален и всегда с fallback** — `null`-вердикт обрабатывается

явно: цензура пропускает текст, сравнение отправляет ДЗ в модерацию.

6. **Одобренный текст защищён** — перезапись `text` возможна только через

AI-улучшение той же формулировки или явное ✅ админа.

7. **Цензура до записи в БД** — отклонённый текст не оставляет следов.

8. **Единые источники**: тексты — `messages.ts`, ошибки — `errors.ts`,

даты — `weeks.ts`, сокращения предметов — `subjects.ts`.
