# План рефакторинга UI и улучшений SchoolBot

Ветка: `refactoringUI_AI`

## 0. Файлы для изучения (читать в первую очередь)

Чтобы понять проект, изучать в таком порядке:

1. `prisma/schema.prisma` — модели данных (Homework, Additional, настройки расписания)
2. `src/app/api/telegram/webhook/route.ts` — точка входа вебхука Telegram, здесь сейчас затычка вместо ошибок
3. `src/bot/bot.ts` — создание бота, регистрация всех хендлеров
4. `src/bot/keyboards.ts` — все клавиатуры (сейчас всё inline, будет переезд на reply)
5. `src/bot/messages.ts` — шаблоны сообщений, здесь `adminReviewMessage` и затычка `HOMEWORK_EMPTY_TEXT` для oldText
6. `src/bot/handlers/` — `start.ts`, `schedule.ts`, `homework.ts`, `additional.ts`, `admin.ts` — флоу пользователя
7. `src/services/homework.service.ts` — логика сохранения ДЗ, здесь возникает `oldText: null` (ветка `!existing`)
8. `src/lib/ai.ts` — текущий AI-вызов `compareHomework` (сверка ДЗ через OpenRouter)
9. `src/lib/schedule-template.ts` — шаблон расписания с полными названиями предметов
10. `src/types.ts` — текущий свалок типизации, будет разделён

## Общие правила для всех задач

- **Типизация**: вся типизация выносится в файлы типов (`src/types/*.ts`), в файлах с логикой (хендлеры, сервисы, либы) типов не пишем — только импортируем. `src/types.ts` разделяется на тематические файлы.
- **Ошибки**: все ошибки — через единый реестр (см. задачу 1). Никаких затычек, молчаливых catch и «просто текста» в ответах.
- **Без tests/demo в промежуточных задачах**: не пишем тесты и демо-данные по ходу работ.
- **Тесты в конце и минимальные**: одна финальная задача, минимальный объём, агента не перегружать.
- **Документацию не пишем и не просим** — она будет делаться отдельно после полного рефакторинга.
- В задачах ниже — флоу и ссылки на файлы, не готовый код.

## Задача 1. Реестр ошибок + ответ вебхука

**Цель**: все ошибки в одном месте, вебхук всегда отвечает структурированно.

Флоу:
1. Создать реестр ошибок: единый список кодов с юзер-френдли сообщениями (по образцу того, как ошибки уже вынесены в других частях бота — посмотреть, как это сделано в существующих частях, и привести вебхук к тому же виду).
2. `src/app/api/telegram/webhook/route.ts`: обернуть обработку апдейта в try/catch. При любой ошибке отвечать HTTP 200 (Telegram не должен ретраить и дублировать апдейты), но в теле — JSON вида `{ ok: false, error: { code, message } }`. При успехе — `{ ok: true }`.
3. Пройтись по всем хендлерам и сервисам: убрать затычки и «просто текст» в catch — вместо этого возвращать/бросать ошибку из реестра, чтобы она попала и в ответ вебхука, и в логи в едином формате.

Ссылки: `src/app/api/telegram/webhook/route.ts`, `src/bot/bot.ts`, все файлы в `src/bot/handlers/`, `src/services/`.

## Задача 2. Вынос типизации в файлы типов

Флоу:

2. Перенести туда все интерфейсы/типы, которые сейчас объявлены внутри хендлеров, сервисов и либ (например `SaveHomeworkResult` в `homework.service.ts`, params-типы сообщений в `messages.ts`).
3. В файлах логики оставить только импорты типов.

Ссылки: `src/types.ts`, все файлы, где сейчас объявлены локальные интерфейсы (grep по `interface ` и `type ` в `src/`, исключая `src/types.ts`).

## Задача 3. Фикс oldText в adminReviewMessage

**Цель**: убрать затычку, сделать null невозможным по типам.

Контекст (проверено по коду): `oldText: null` возникает ровно в одном месте — `src/services/homework.service.ts`, ветка `!existing`, когда ДЗ создаётся **впервые**. Во всех остальных ветках (замена, kept, pending) `oldText: existing.text`, а `text` в БД обязателен — при замене oldText физически не может быть null. Проблема только в том, что тип разрешает null везде.

Флоу:
1. В типах (задача 2) разделить результат сохранения на два кейса: «ДЗ создано впервые» — вообще без поля oldText; «ДЗ заменено» — `oldText: string`, строго обязательный.
2. `adminReviewMessage` принимает этот union: для первого кейса в уведомлении админу пишем «Новое ДЗ (старого текста не было)», для второго — блок «Прошлое ДЗ: …» со строгим string.
3. Удалить затычку `HOMEWORK_EMPTY_TEXT` из `src/bot/messages.ts` — она больше не нужна.

Ссылки: `src/services/homework.service.ts` (ветка `!existing`), `src/bot/messages.ts` (adminReviewMessage), `src/bot/handlers/homework.ts` (место формирования params), `src/types/` (из задачи 2).

## Задача 4. Reply-клавиатура: переезд навигации

**Цель**: навигация — кнопками под полем ввода, полностью контекстно; уроки — inline.

Решения (согласованы):
- Reply-клавиатура полностью контекстная: перерисовывается на каждом шаге, как сейчас inline.
- Главное меню, недели (прошлая/текущая/следующая), дни недели — всё в reply.
- Дни недели — просто «Пн Вт Ср Чт Пт», без списка уроков в кнопках.
- Выбор урока после выбора дня — inline-кнопками в сообщении, с кнопкой «« Дни» для возврата.
- Админ-кнопки «Одобрить/Отклонить» остаются inline в сообщении с ДЗ.

Флоу:
1. Переписать `src/bot/keyboards.ts`: фабрики reply-клавиатур (главное меню, недели+дни, дни) и inline-клавиатуры (уроки выбранного дня, навигация «« Дни»/«Меню», админ-подтверждение).
2. Хендлеры переключаются: меню/недели/дни теперь приходят как обычные текстовые сообщения (нужен маппинг текста кнопки → действие, тексты кнопок вынести в константы, чтобы хендлеры и клавиатуры не разъехались). Уроки остаются callback_query.
3. `handlers/start.ts`: при /start отправлять главное меню reply-клавиатурой.
4. `handlers/schedule.ts`: флоу «Расписание → неделя → день → список уроков» — недели и дни через reply, вывод уроков сообщением.
5. `handlers/homework.ts` и `handlers/additional.ts`: флоу выбора дня/урока аналогично; после выбора урока — inline-клавиатура уроков с возвратом «« Дни».
6. Проверить, что сцены/состояния (если используются в `bot.ts`) корректно реагируют на текстовые нажатия reply вместо callback.

Ссылки: `src/bot/keyboards.ts`, `src/bot/bot.ts`, `src/bot/handlers/start.ts`, `schedule.ts`, `homework.ts`, `additional.ts`.

## Задача 5. Сокращение «Физра»

**Цель**: «Физическая культура и здоровье» → «Физра» везде. Остальные предметы не трогаем — они короткие и в кнопки помещаются.

Флоу:
1. Одна функция/константа в одном месте (например `src/lib/subjects.ts`): маппинг только для физкультуры, для остальных — имя как есть.
2. Применить во всех местах вывода предметов: inline-кнопки уроков, списки уроков в сообщениях, тексты ДЗ, админ-уведомления.
3. В БД и шаблоне расписания названия не меняем — сокращение только на слое вывода.

Ссылки: `src/lib/schedule-template.ts`, `src/bot/keyboards.ts`, `src/bot/messages.ts`, `src/services/schedule.service.ts`.

## Задача 6. AI-цензура текста ДЗ и «Дополнительно»

**Цель**: нельзя записать в ДЗ/«Дополнительно» текст не по делу (спам, мат, не домашка).

Решения (согласованы):
- Отдельный вызов AI (не объединять с `compareHomework`) — цензура будет использоваться и в «Дополнительно», где сравнивать не с чем.
- При отклонении — запись не сохраняется вообще, бот сразу отвечает отказом.

Флоу:
1. В `src/lib/ai.ts` добавить отдельную функцию цензуры: промпт «является ли текст домашним заданием / записью по делу», ответ — структурированный вердикт (по делу / не по делу). Использовать тот же механизм вызова, что и существующий `compareHomework`.
2. В флоу добавления ДЗ (`handlers/homework.ts`): после ввода текста, до сохранения и до/параллельно со сверкой — вызов цензуры. Если не по делу — ответ юзеру отказом из реестра ошибок (задача 1), запись не создаётся.
3. В флоу «Дополнительно» (`handlers/additional.ts`) — та же проверка перед сохранением.
4. Обработать сбой AI (таймаут/ошибка): решать через реестр ошибок — при недоступности AI запись отклонять или пропускать проверку, но поведение должно быть явным и единым для обоих флоу.

Ссылки: `src/lib/ai.ts`, `src/bot/handlers/homework.ts`, `src/bot/handlers/additional.ts`, `src/services/homework.service.ts`, `src/services/additional.service.ts`.

## Задача 7. Хранилище юзеров

**Цель**: учёт юзеров в БД: id, username, ник, дата регистрации. Без проверки на каждом сообщении.

Решения (согласованы):
- Записываем только при /start, upsert (повторный /start обновляет username/ник).
- В админ-уведомлении на ручную проверку показывать не только id, но и username и имя.

Флоу:
1. `prisma/schema.prisma`: модель User — telegramId (уникальный), username, имя/ник, registeredAt. Миграция.
2. `handlers/start.ts`: при /start — upsert юзера по telegramId.
3. `adminReviewMessage` (и другие админ-уведомления): рядом с id выводить username и имя. Для этого в момент формирования уведомления подтягивать юзера из БД по telegramId автора записи; если юзера нет (старые записи до внедрения) — показывать просто id, без падения.

Ссылки: `prisma/schema.prisma`, `src/bot/handlers/start.ts`, `src/bot/messages.ts`, `src/services/homework.service.ts`.

## Задача 8. Финальная минимальная проверка

**Цель**: убедиться, что ничего не сломано. Минимально, без перегруза.

Флоу:
1. Один прогон сборки/типчеков проекта.
2. Ручной чек-лист в боте: /start → меню reply → Расписание → неделя → день → уроки inline → «« Дни» → Добавить ДЗ → цензура (нормальный текст проходит, мусор отклоняется) → админ-уведомление (username + имя, «новое ДЗ» без oldText, замена — с oldText) → Одобрить/Отклонить → Дополнительно с цензурой.
3. Опционально один минимальный smoke-тест на реестр ошибок и формат ответа вебхука. Больше ничего не писать.
